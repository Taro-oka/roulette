# Roulette

チームの雑談ルーレット用に作った、参加者の名前でまわすルーレットアプリです。

## 概要

- 参加者を登録すると、人数に応じて等分されたルーレットが表示される
- 「GO」ボタンで回転し、止まった位置の参加者を `alert` で表示する
- 参加者の追加・削除は設定画面（`/settings`）から行う

## 動機

- 雑談ルーレットをチームでやっていて、自力で作るとどうなるか試したかった
- 最近自分でコードを書かないので、たまにはAIに頼らず書いてみたかった

## 使用技術

| 分類 | 技術 |
| --- | --- |
| フレームワーク | React 19 / TypeScript |
| ビルド | Vite |
| スタイリング | Tailwind CSS v4 |
| ルーティング | React Router v7 |
| バリデーション | Zod（localStorage から読んだデータのパース） |
| データ保存 | localStorage |
| ルーレット描画 | CSS `conic-gradient` / Web Animations API |

### 起動方法

```bash
npm install
npm run dev
```

## 前提・方針

- 本格的にやるなら Canvas API を使うことになりそうだが、慣れ親しんだ DOM + CSS の領域でやってみたかった
- レスポンシブは面倒だったので非対応
- エディタ内ではAI不使用、コード生成も基本させず、自分で考える or 検索することにした（どうしても聞いた点は[後述](#どうしてもaiに頼った点)）
- 今回の焦点はルーレットで、バックエンドを作るほどでもないので、データ保存は localStorage で代用した

## 工夫点

### 1. 回転アニメーションは Web Animations API で制御

CSS アニメーションで作るつもりだったが、停止時のルーレットの角度をランダムに決める必要があり、CSS だけでは表現しづらかった。そのため、JavaScript から制御できる Web Animations API（`element.animate()`）に切り替えた。

仕組み（[Roulette.tsx](src/pages/home/components/Roulette.tsx) の `rotate`）:

1. `getRandomDeg` で停止角度 `targetDeg`（0〜359）をランダムに決める
2. `rotate(0)` から `rotate(360° × 8周 + targetDeg)` までのアニメーションを `animate()` で実行する（時間・イージングは [constants](src/pages/home/constants/index.ts) で設定。7秒かけて減速する）
3. `await animation.finished` で終了を待ち、`targetDeg` から当たりの参加者を判定して `onAnimationEnd` で通知する

細かい配慮:

- `targetDeg` が区切り線の真上にならないよう、人数が割り切れる場合は区切り線の角度を除外している（`blackList`）
- 連打された場合は、最後に押した回転の結果だけを通知する（`rotationRef` のカウンタで判定）
- 画面遷移などでコンポーネントが破棄されたときに通知が飛ばないよう、アンマウント時にも同じカウンタを進めている

### 2. 名前の配置（一番難しかった）

一番苦労したのが、各セクションの中に名前を配置するところ。次の手順で、セクションの中に収まる長方形を作り、その中に名前を入れている。

1. ルーレットの中心から、各区切り線の外周上の端点を三角関数で求める
2. 隣り合う区切り線それぞれについて、中心〜端点を 1:3 に内分する点を `dividePoints` で求める
3. その2点を結ぶ線を底辺として、外側（左方向）に 1px ずつ伸ばし、外周を超える手前までを長方形の「幅」とする（`getLeftOffsetPoint` を使用）
4. 長方形の高さは2点間の距離。この長方形を `translate` と `rotate` でセクションの位置に合わせ、中央に名前を置く

## どうしてもAIに頼った点

- `getLeftOffsetPoint` の実装（[src/utils/math.ts](src/utils/math.ts)）
  - 点 a → b の向きに対して、b を起点に左方向へ n 進んだ座標を返す関数
  - a → b のベクトルを 90° 回転して左向きにし、長さ 1 に正規化してから n 倍して b に足す、という計算
  - ベクトルの知識が抜けていて、自力では組み立てられなかった
- この README のフォーマット整えと文章生成

## 感想

- すべて自分で考えて実装したので、内容を全て把握していて、バグが出ても場所がすぐイメージできた。AI時代以前の開発の楽しさを思い出した
- 開発環境を立ち上げるだけで、Web 上の記事とバージョンが合わず無駄な時間を使った。この辺りはAIに全部任せられるので、本当に楽になったと実感した
- 三角関数やベクトルといった高校数学を久しぶりに使った。三角関数はなんとか覚えていたが、ベクトルは完全に抜けていて、「そもそもベクトルとは」というところから復習が必要だった。数学ⅡBはセンター試験で一番得点率が低かった科目なので無理もない

## 客観評価

AIがリポジトリ全体のコードと設計を読んで書いた評価。実施したのはソースの読解、型チェック（`tsc -b`、エラーなし）、`eslint`（エラー0・警告1）まで。ブラウザでの動作確認と `vite build` は実行していない。リポジトリにテストはない。

### 良い点

**コード**
- 技術選定に理由がある。「停止角度をランダムに決めたい」という要件から、CSS アニメーションではなく Web Animations API を選んでいる
- 非同期まわりの配慮がある。連打時に最後の1回だけを通知する処理、アンマウント時に通知しない処理、区切り線の真上で止まらないようにする処理（`blackList`）が入っている
- `utils/math.ts` の関数は小さな純関数で、名前が内容を表していて、コメントもある。名前の配置という難しい計算を、内分点・ベクトルの回転・三角関数で自力で組み立てている
- TypeScript の `strict` と `noUnusedLocals` を有効にしていて、型チェックは通る

**設計**
- `api` / `utils` / `types` / `pages` に分かれていて、localStorage へのアクセスは `api` に閉じている。保存先を変える場合の影響範囲が狭い
- 型を Zod のスキーマから導出し、localStorage から読んだデータを境界で検証している
- 「ルーレットが主役」という焦点に対して、バックエンドを作らない、レスポンシブは対応しない、といった割り切りが明確

**運用**
- コミットは小さく、日本語のメッセージで何をしたか分かる。AIを使わなかった点と例外も README に正直に書かれている

### 改善の余地

影響が大きい順。いずれも動作を壊すものではなく、拡張や保守をするときに効いてくる点。

1. **`Roulette.tsx` に責務が集まっている**。幾何計算、アニメーション制御、描画が約250行の1ファイルにある。計算部分を純関数に切り出せば、テストしやすくなり、コンポーネントも短くなる。当たりの判定（角度からインデックスを求める処理）は、テストの効果が特に大きい
2. **寸法の二重管理**。`RADIUS = 250` と、Tailwind のクラス（`w-125`、`h-62.5`）が別々に書かれていて、片方だけ変えると計算がずれる
3. **DOM への依存が必要以上に残っている**。`centerOf` で取得した中心は、各点の差分を求める原点としてしか使われていない。原点を `(0, 0)` にすれば DOM の計測なしで計算できる。また `useLayoutEffect` は `initialized` で守られていて、実質マウント時の1回だけ動く。参加者を変更しても再計算されないが、現状は設定画面の保存後に `window.location.reload()` するので成り立っている
4. **設定画面の state 管理**。`_prev[index].name = name` は、配列を浅くコピーしただけで元のオブジェクトを書き換えている。参加者一覧と追加欄で `input` の `id` が重複する（どちらも `0` から始まる）。リストの `key` にインデックスを使っている
5. **`api/participant.ts` の未使用関数**。読んだ範囲では `addParticipant`、`updateParticipant`、`deleteParticipant` はどこからも使われておらず、設定画面にある同名のローカル関数と紛らわしい
6. **エラー処理がない**。localStorage の中身が壊れていると、`JSON.parse` か Zod が例外を投げ、画面が表示されなくなる
7. **計算の簡素化**。`getRequiredDistancesToEnd` は象限ごとの4分岐だが、`x = sin(θ) × R`、`y = -cos(θ) × R` の1式で同じ結果になる（4象限とも一致することを確認した）。長方形の幅を 1px ずつ伸ばして外周との交点を探す `while (true)` も、式で直接求められる。上限のないループなので、条件が崩れると止まらない
8. **境界のエッジケース**。人数が割り切れない場合は `blackList` が空になり、停止角度が 0（ポインターが最初の区切り線の真上）になる可能性が約 1/360 で残る。実害は小さいが、割り切れる場合の処理と揃っていない
9. **設定ファイルの残骸**。`_tsconfig.app.json` と `_tsconfig.node.json` は、名前を変えて使われていないように見える。Tailwind v4 と `@tailwindcss/vite` の構成では通常不要な `tailwindcss-cli`、`autoprefixer`、`postcss`、`tailwind.config.js` も残っている（実際に不要かは未確認）
10. **未完成の部分**。`Header` と `About` はプレースホルダーのまま。`eslint` の警告 1 件（`useEffect` のクリーンアップで `ref` の値を使っている）は、ref を意図的に書き換える処理なので、意図をコメントで残すと分かりやすい
11. **作品としての見せ方**。スクリーンショットやデモのリンクがなく、テストもない

### 総評

規模は小さいが、「自力で作る」という目的に対して、設計・実装・記録まで一貫している。力量が出ているのは、名前の配置を数学で解いた部分と、非同期処理まわりの配慮。構成は素直で、型チェックも通る。一方で、改善点のほとんどは、`Roulette.tsx` に集まった責務の整理と、小さな使い残し・重複の解消に収まる。この2つを直し、判定ロジックのテストとデモを足せば、作品としての完成度と伝わり方がもう一段上がる。
